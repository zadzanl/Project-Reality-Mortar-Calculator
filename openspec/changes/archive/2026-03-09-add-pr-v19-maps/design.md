## Context

The mortar calculator supports 83 maps from PR:BF2 v1.8 and earlier. PR v1.9 (Feb 27, 2026) added two new maps — `talbisah` (2×2 km) and `icebreaker` (4×4 km). No physics or coordinate system changes were made. The existing processing pipeline (`collect_maps.py` → `process_maps.ipynb` → `generate_contours.ipynb`) is fully functional and handles new maps without code changes — it just needs to be run against the updated game installation.

A secondary issue exists: `mapsList.json` is a static file used only by the Android/offline build. It is not auto-generated by any script in the repo. The Flask server generates the equivalent list dynamically from `processed_maps/` at runtime. This means `mapsList.json` requires manual updates whenever maps are added, which is error-prone.

## Goals / Non-Goals

**Goals:**
- Process `talbisah` and `icebreaker` through the full pipeline (collect → heightmap → contour)
- Update `mapsList.json` to include both new maps (count: 83 → 85)
- Create a simple script to auto-generate `mapsList.json` from `processed_maps/`
- Document `the_falklands` exclusion in `processed_maps/README.md` and `AGENTS.md`

**Non-Goals:**
- Processing `the_falklands` (intentionally excluded — non-standard 8km+ boundary)
- Modifying the processing pipeline code (no pipeline changes needed)
- Modifying frontend code (auto-discovery handles new maps)
- Changing physics constants or ballistics logic
- Updating existing map data (v1.9 didn't change any terrain heightmaps)

## Decisions

### 1. Run existing pipeline as-is (no code changes to processors)

**Rationale:** The `collect_maps.py`, `process_maps.ipynb`, and `generate_contours.ipynb` pipeline is designed to handle arbitrary new maps. Adding `talbisah` and `icebreaker` is a data operation, not a code change.

**Alternative considered:** Modify `process_one_map.py` to process individual maps from command line. Rejected because the notebook pipeline already supports selective processing and provides better visibility.

### 2. Create `processor/generate_maps_list.py` as a standalone script

**Rationale:** A simple script that scans `processed_maps/` for folders containing `metadata.json` and writes `mapsList.json` mirrors the Flask server's `/maps/list` logic. This eliminates manual drift between processed maps and the static manifest.

**Alternative considered:** Integrate into `process_maps.ipynb`. Rejected because `mapsList.json` is only needed for Android builds, and the notebook is already long. A standalone script can be called from `build-android.bat` or run independently.

### 3. Document `the_falklands` exclusion rather than processing it

**Rationale:** `the_falklands` has a non-standard map size (primary game area is 8km × 8km, but airfields and a helicopter carrier extend beyond this boundary, making the total area significantly larger). The processing pipeline's default size inference would likely produce incorrect results. This needs special handling in a separate change.

## Risks / Trade-offs

- **[Risk] Map folder names don't match expected convention** → Mitigation: `collect_maps.py` auto-detects map folders from the PR installation. The folder names `talbisah` and `icebreaker` follow PR's standard lowercase naming convention. Verify after collection that folders match expected names.
- **[Risk] `mapsList.json` generation script could mask missing processed data** → Mitigation: Script only includes maps that have a valid `metadata.json`. Maps with incomplete processing (missing heightmap, contour, etc.) are excluded.
- **[Risk] Contour generation requires scipy/matplotlib not available in all environments** → Mitigation: Use same environment (Google Colab or local Jupyter) that was used for all 83 existing maps. Dependencies are already documented in `processor/README.md`.
